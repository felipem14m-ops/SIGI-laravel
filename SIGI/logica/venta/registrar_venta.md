# Registrar Venta (Punto de Venta POS)

La lógica de esta funcionalidad se maneja principalmente desde el controlador `VentaController.php` y las vistas `Admin/Venta/ListasdeVentas.blade.php` y `Admin/Venta/facturaPOS.blade.php`.

Para realizar esta acción, el cajero o administrador autenticado interactúa con la opción "Punto de Venta" que se encuentra en el menú lateral izquierdo del panel de administración, dentro de la sección "Gestión Comercial". Este enlace está configurado para redirigir al controlador `VentaController.php` a través de la ruta con nombre `ventas.index`, que corresponde a la URL `/ventas` mediante una petición `GET`. Esta ruta está protegida por el middleware `auth`, lo que garantiza que únicamente los usuarios con sesión activa puedan acceder a la consola del terminal POS.

Al momento de recibir la petición `GET`, el controlador ejecuta el método `index` de la clase `VentaController`. Este método realiza consultas a la base de datos a través de los modelos `Producto`, `Categoria`, `MetodoPago` y `Venta`. Específicamente, consulta los productos cuyo estado sea `activo` y posean `stock_actual` mayor a cero cargando su relación con la categoría mediante `with('categoria')`, obtiene las categorías activas, los métodos de pago habilitados (`MetodoPago::where('activo', 1)`), y calcula la suma total de ingresos del día actual filtrando las ventas con fecha del día en estado `completada`. Todos estos datos se empaquetan con la función `compact` y se envían a la vista `ListasdeVentas.blade.php`. Esto permite que el terminal POS construya dinámicamente el catálogo de productos disponibles, los botones de filtro por categoría y los métodos de pago habilitados en la consola de cobro.

En la vista `ListasdeVentas.blade.php`, el usuario interactúa dinámicamente agregando productos al carrito mediante funciones JavaScript (`agregarAlCarrito`). El sistema calcula en tiempo real en el cliente el subtotal por ítem y el total general a cobrar. Cuando el usuario hace clic en el botón "FINALIZAR VENTA (F10)", el sistema despliega un diálogo interactivo de SweetAlert2 que solicita ingresar el "Monto Recibido" en efectivo. A medida que el usuario digita la cantidad recibida, el sistema calcula automáticamente el "Cambio a Entregar" de forma inmediata en pantalla.

Al confirmar el pago en el SweetAlert2, el script cliente realiza una petición asíncrona `POST` mediante `fetch` a la ruta con nombre `ventas.store` (URL `/ventas`), enviando un objeto JSON con el arreglo de ítems del carrito (`id`, `nombre`, `precio`, `cantidad`), el identificador del método de pago (`metodo_pago_id`), el total calculado, el monto recibido y el cambio a devolver. Esta petición viaja acompañada del encabezado `X-CSRF-TOKEN` para garantizar la seguridad de la transacción.

La petición `POST` es recibida por el método `store` del controlador `VentaController`. Lo primero que ejecuta este método es una validación de los datos recibidos mediante `$request->validate`. Se verifica que el arreglo `items` contenga al menos un producto, que cada `id_producto` exista en la tabla `productos`, que la cantidad sea un entero positivo mayor o igual a 1, y que el `metodo_pago_id` exista en la tabla `metodos_pago`. Si alguna validación falla, Laravel retorna una respuesta JSON con código de error HTTP 422 y los detalles del fallo.

Una vez superada la validación, el controlador inicia una transacción atómica de base de datos utilizando `DB::transaction()`. Dentro de la transacción, el controlador obtiene el tipo de movimiento de inventario con código `SALIDA` a través del modelo `TipoMovimiento`. A continuación, se crea el registro de la venta en la tabla `venta` mediante `Venta::create()`, asignando el `id_usuario` del usuario autenticado (`Auth::id()`), el `id_metodo`, la `fecha_venta` actual (`now()`), el estado `completada` y un total inicial en cero.

Seguidamente, el controlador recorre cada ítem del carrito en un ciclo `foreach`. Para garantizar la consistencia en entornos concurrentes, bloquea la fila del producto en la base de datos utilizando `Producto::lockForUpdate()->findOrFail($item['id'])`. El controlador verifica estrictamente que el `stock_actual` del producto sea mayor o igual a la cantidad solicitada; si el stock es insuficiente, se lanza una excepción `\Exception` que revierte inmediatamente toda la transacción (`rollback`), evitando registros incompletos o inconsistencias. Si hay stock disponible, se calcula el subtotal por producto, se acumula en la variable del total general, y se inserta la línea correspondiente en la tabla `detalleventa` mediante `DetalleVenta::create()`.

Para garantizar una trazabilidad completa e ininterrumpida entre el módulo de ventas y el módulo de inventario, el controlador descuenta la cantidad vendida del `stock_actual` del producto, guarda el nuevo saldo con `$producto->save()`, y genera automáticamente un registro de auditoría en la tabla `movimiento_inventario` a través del modelo `Movimiento::create()`. Este registro almacena el `id_producto`, el `id_usuario`, el `id_tipo_movimiento` (Salida por Venta), la `cantidad` vendida, el `stock_anterior`, el `stock_resultante`, la `fecha` actual y el motivo formateado como `"Venta #" . $venta->id_venta`.

Finalmente, al terminar de procesar todas las líneas, el controlador actualiza el registro principal de la venta con el `total` definitivo acumulado, el `monto_recibido` y el `cambio` calculado, retornando una respuesta JSON exitosa con el campo `venta_id`. En el frontend, el navegador muestra un mensaje emergente confirmando el registro de la venta junto con el cambio a entregar, e incluye el botón "🖨️ Imprimir / Descargar Factura POS" que ejecuta la función `imprimirTicketVentaDirecto()`, abriendo la vista de impresión del ticket térmico en 80mm de forma transparente y sin redirigir ni recargar la consola del POS.
